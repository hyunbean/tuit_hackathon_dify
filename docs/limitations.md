# 한계 (Limitations) — 전문

> README `## 한계` 절의 상세판입니다. 각 항목을 **한계 → 원인 → 해결 방법** 형식으로 기술합니다.
> 새로운 사실을 추가하지 않고, 기존 서술을 재구성만 했습니다.


- **"60/60 100%"는 튜닝에 쓴 골든셋으로 잰 수치다** → 실패 3건(N08/N18/N40)을 진단·패치하는
  데 쓴 바로 그 골든셋으로 재확인했기 때문에 낙관 편향이 있다(tuning-on-the-eval-set) →
  N08/N18/N40을 제외한 나머지 57건에서 고정 시드(20260728)로 15건을 뽑아 별도 holdout
  재측정을 진행했고, 결과는 14/15(93%)로 더 보수적이다 (`eval/golden/holdout_2026-07-28/`,
  `eval/run_holdout.py`).
- **N40(단위 매핑)이 패치 후에도 재현 시 불안정하다** (4회 중 3회 실패·1회 성공, 2026-07-22 확인)
  → 상품코드 확신도와 단위 확신도를 단일 `matchConfidence` 필드에 합쳐서 판단하고 있어,
  단위만 틀려도 사람 검토로 넘어가지 않는다 → 단위 매핑을 별도 필드로 분리해 독립적으로
  신뢰도를 매기면 근본적으로 해결된다.
- **오타 케이스 일반화가 부족하다** — holdout에서 새로 발견된 N07(`pomidorr` 오타)이
  `UNKNOWN`으로 실패했다 → N08/N18/N40 수정은 그 3건의 특정 오타·동형이의어 패턴에만
  국소적으로 적용된 프롬프트 패치였고, "오타 일반"에 대한 강건성은 다루지 않았다 → 골든셋을
  확장해 다양한 오타 패턴을 포함시키고, 얕은 문자열 매칭 대신 더 강건한 매칭 전략을 검토해야 한다.
- **Product Normalizer의 꼬리 지연이 평균보다 훨씬 길다** (`[사후측정 2026-07-28]`,
  p95 12.29s, 평균 4.62s의 2.7배) → 원인이 아직 진단되지 않았다(지식베이스 검색 슬롯 경쟁,
  네트워크 변동 등 후보는 있으나 확정되지 않음) → 개별 케이스별 노드 단위 타이밍 로그를
  추가해 어느 노드가 꼬리를 만드는지 특정해야 한다.
- **Price Insight/Report Inspector의 p95/p99는 표본이 작아(n=10) 신뢰할 수 없다** → 골든셋
  케이스 수 자체가 각 10건뿐이라 p95가 사실상 상위 1~2개 관측값에 불과하다 → 골든셋을
  확장해(아래 항목 참고) 표본 크기를 늘려야 유의미한 꼬리 지연 통계를 얻을 수 있다.
- **해커톤 당시의 실행 로그가 남아 있지 않다** — 본 README의 실측 수치는 전부 이 저장소의
  DSL을 Dify에 재-import해 2026-07-22 이후 재현한 것이며 해커톤 당일 기록이 아니다 → 당시
  로깅/아카이빙 체계가 없었다 → 향후 프로젝트에서는 실행 로그를 저장소에 커밋하거나
  아티팩트로 보관하는 절차를 표준화해야 한다.
- **LLM 출력 검증이 수동 JSON 파싱에 의존한다** → 워크플로우 설계 당시 Dify LLM 노드의
  structured output(JSON Schema) 기능을 쓰지 않았다 → 해당 기능으로 전환하면 코드 노드의
  수동 파싱·검증 로직을 줄일 수 있다.
- **금칙어 필터가 영어/한국어/러시아어만 지원한다** → 초기 설계 범위가 그 세 언어로
  한정됐다 → 우즈베크어 금칙어 표현을 조사해 필터를 확장해야 한다.
- **invalid 분기의 fallback 메시지가 영어/한국어만 지원한다** → 다국어 대응이 부분적으로만
  구현됐다 → 우즈베크어/러시아어 fallback 메시지를 추가해야 한다.
- **골든셋 크기와 정확도 기준선에 CI gate가 없다** → 회귀 평가는 실행되지만 특정 정확도
  임계치 미달 시 CI를 실패시키는 게이트는 아직 없다 → 현지 팀원 검수를 거친 실사용 표현으로
  골든셋을 확장하고, 정확도 목표치 기반 CI gate를 추가해야 한다.
