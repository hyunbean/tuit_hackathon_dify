# Product Normalizer 골든셋 재측정 — 3건 실패 진단 → 수정 → 재측정 (2026-07-22)

> `docs/postmortems/README template`에 따라 `POSTMORTEM_TEMPLATE.md`를 채운 문서입니다.
> 아래 내용은 새로운 사실을 추가하지 않고, `README.md`의 "실측 결과(2026-07-22 재현 평가)"
> 절(§평가 하네스, `README.md:128-243` 부근)과 커밋 `5ceba02`("Add live eval results and
> fix normalizer prompt gaps")의 커밋 메시지·diff를 재구성한 것입니다.

## 발생 현상 (What Happened)

- 2026-07-22, 이 저장소의 DSL 3종을 Dify에 재-import해 골든셋 60케이스(정규화 40 /
  가격 설명 10 / 제보 검수 10)로 1차 회귀 평가를 실행했다.
- 결과: 60건 중 3건 실패, 57/60(95%). 실패는 전부 Product Normalizer(37/40, 92%)에서
  발생했고, Price Insight Explainer·Report Inspector는 각각 10/10(100%)이었다.
- 실패한 3건은 모두 우즈베크어 입력이었다: `N08`(`bodring` → 기대값 `CUCUMBER`),
  `N18`(`olma` → 기대값 `APPLE`), `N40`(`piyoz bir bog'` → 기대값 `ONION` + 단위
  `BUNDLE`).
- 영향 범위: Product Normalizer 워크플로우의 정확도 지표(README §실측 결과 1차 측정 표)와,
  그 뒤를 잇는 재측정 전체 과정(README §"normalizer 실패 3건 진단 → 수정 → 재측정").

## 발견 경위 (How It Was Found)

- `eval/run_eval.py`로 골든셋 60케이스를 실제 Dify API에 대해 실행하는 회귀 평가
  (`eval/scoring.py`의 결정론적 채점, LLM-as-judge 아님) 도중 발견됐다.
- 실패 3건이 전부 우즈베크어 케이스라는 공통점이 관찰되면서 원인 조사가 시작됐다
  (README: "전부 우즈베크어여서 원인을 추적했다").

## 원인 분석 (Root Cause)

README에 기록된 진단 순서 그대로, 가설을 세우고 반증하는 과정을 거쳤다:

1. **가설 1 — 커버리지 부족 (기각)**: 지식베이스(`kb/product-alias-guide.md`)에 세 별칭이
   모두 이미 등록돼 있었다. 즉 원본 문서 자체의 누락은 아니었다.
2. **가설 2 — 지식베이스 미연결 (기각)**: 검색 로그를 확인한 결과 해당 문서가 실제로
   검색되고 있었다(311회 조회). 즉 Knowledge Retrieval 노드 연결 자체의 문제는 아니었다.
3. **가설 3 — 검색 슬롯 경쟁 (확인, 그러나 완화책은 반전돼 원복)**: 지식베이스 문서 3개
   (`product-alias-guide.md`, `price-copy-guide.md`, `safety-copy-guide.md`)가 단일
   데이터셋을 공유하는데, `top_k`가 작아 필요한 청크가 밀려나는 것을 확인했다. `top_k`를
   3→10으로 늘려 재측정했더니 예상과 반대로 정확도가 92%→90%로 **더 나빠졌다**(오타·다국어
   케이스 2건이 새로 깨짐). 2회 재현해 동일한 결과를 확인한 뒤 원복했다 — "검색 범위를
   넓히면 정확도가 오른다"는 직관이 이 경우엔 틀렸다는 것이 근거로 확인됐다.
4. **실제 수정 — 프롬프트 국소 패치**: 전역 설정 대신, 기존에 `pomidor`/`tuxum`/`guruch`
   등을 하드코딩했던 것과 동일한 패턴으로 시스템 프롬프트에 `bodring`·`olma`·`bog'` 규칙
   3줄을 직접 추가했다(커밋 `5ceba02`, `BozorCheck_Product_Normalizer_v1.yml` diff).
   → 92%→98%로 개선, N08·N40 해결.
5. **우즈베크어 동형이의어 발견**: `olma`(사과)만 남은 실패를 재조사한 결과, 지식베이스의
   안전문구 문서(`kb/safety-copy-guide.md`)에 있는 `sotib olmang`("사지 마세요")과 어간이
   겹쳐 `olma`가 부정명령형("가져가지 마라")으로 오인되고 있었다. 동형이의어를 명시적으로
   해소하는 문장으로 프롬프트를 교체해 최종 해결했다.
6. **재현 검증 중 스스로 뒤집은 판단**: 패치 후 3회 연속 실행에서 "N18은 고쳐졌는데 N40이
   깨졌다"는 패턴이 보여 "긴 규칙이 옆 규칙을 밀어낸다"는 가설을 세웠으나, 4번째 실행에서
   N40도 통과해 그 가설을 스스로 기각했다. 원인은 `temperature=0.1`에서도 남아 있는
   LLM의 확률적 변동으로 재평가됐다.

## 조치 (Remediation)

- 시스템 프롬프트에 `bodring`(→ CUCUMBER), `olma`(→ APPLE, `sotib olmang`과의 동형이의어
  명시적 해소 포함), `bog'`/`bir bog'`(→ 단위 BUNDLE) 규칙을 직접 추가했다
  (`BozorCheck_Product_Normalizer_v1.yml`, 커밋 `5ceba02`).
- `top_k` 3→10 변경은 재현된 악화(92%→90%)로 인해 **원복**했다 — 이번 사고에서는 채택되지
  않은 완화책이지만, 반증 과정 자체가 근거로 남아 있다.
- 최종 재측정 결과: Product Normalizer 40/40(100%), 합계 60/60(100%) (README §최종 결과).
- **부분적 조치임을 문서에 명시**: N18(동형이의어)은 패치 후 4회 실행 모두 안정적으로
  해결됐지만, N40(단위 매핑)은 4회 중 3회 실패·1회 성공으로 여전히 불안정하다고 README에
  정직하게 기록돼 있다 — "100%"가 매번 보장되는 결정론적 수정이 아니다.

## 재발 방지책 (Prevention)

- CI(`ci.yml`)에서 mock 모드 스모크 테스트를 상시 실행하고, `DIFY_*` 시크릿이 등록돼 있으면
  push마다 실제 워크플로우를 회귀 평가한다 — 회귀 재발 감지 체계는 이미 존재한다.
- 근본 원인(단일 `matchConfidence`가 상품코드 확신도와 단위 확신도를 모두 떠안는 설계)은
  README "개선하고 싶은 점"에 남아 있으며, 이 문서 작성 시점까지 **미적용**이다 — 단위 매핑을
  별도 필드로 분리해 독립적으로 신뢰도를 매기는 것이 근본적 해결책으로 제안돼 있다.
- 이후(2026-07-28) 이 60/60 수치 자체가 "튜닝에 쓴 골든셋으로 잰 값"이라는 한계가 별도로
  발견되어, N08/N18/N40을 제외한 holdout 15건으로 재측정하는 절차가 추가됐다
  (커밋 `a84ddbd`, README §"⚠️ 위 '100%'는 튜닝에 쓴 골든셋으로 잰 수치다") — 이 자체가
  "같은 데이터로 튜닝하고 같은 데이터로 재확인하지 않는다"는 재발 방지책의 연장선이다.

## 교훈 (Lessons Learned)

- 실패 원인에 대한 첫 직관(가설 1·2)이 틀릴 수 있으므로, 로그로 확인 가능한 근거(별칭 존재
  여부, 검색 조회 횟수)로 가설을 하나씩 반증하는 과정이 실제로 원인(가설 3, 검색 슬롯 경쟁)을
  좁혀냈다.
- "검색 범위를 넓히면 정확도가 오른다"처럼 그럴듯한 직관도 재현 실험(2회 동일 결과 확인)
  없이는 채택하지 않아야 한다 — 이번 사고에서는 그 직관이 실제로는 반대 방향으로 작용했다.
- LLM 기반 시스템에서는 패치가 "고쳤다"와 "이번엔 우연히 통과했다"를 구분하기 어렵다 —
  최소 4회 이상 반복 실행해 재현성을 확인하고, 불안정함이 남아 있다면 "100%"로 반올림하지
  않고 정직하게 기록하는 것이 이 프로젝트가 채택한 원칙이다(이 원칙은 이후 홀드아웃 재측정에도
  그대로 이어졌다).
